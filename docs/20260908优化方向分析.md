## 1. P0 · 数据正确性（会直接影响结论）

### 1.1 北交所标的剔除（决策已定）+ 它暴露的通用缺陷

**现状（实测）**：全项目仅 2 只北交所标的，且**全部来自中证系指数成分**，不是自选股：

| 代码   | 名称     | 来源（权重）                                                                                                                                  |
| :----- | :------- | :-------------------------------------------------------------------------------------------------------------------------------------------- |
| 920599 | 同力股份 | **中证红利价值 1.39%**、中证红利 0.42%、红利价值ETF易方达 1.39%、红利ETF易方达 0.42%、中证红利ETF招商 0.42%；另为 159232 季报持仓 0.21% |
| 920509 | 同惠电子 | 中证全指红利质量 0.04%、红利质量ETF招商 0.04%                                                                                                 |

- 自选股清单（`excel/自选股清单.xlsx` 展示=1，共 51 只）**不含北交所**；国证自由现金流 980092（100 只）**不含北交所**。
- 现状后果：920599 因前缀错误（`_fetch_stock_data.py:69` 把 `920599` 拼成 `sh920599`）K 线冻结在 2026-08-24（仅 7 行），却仍以 `ready:true, rec:true` 出现在 manifest，并以 rank 7 进入推荐 20；`update.py status` 与失败清单均无告警。

**处理原则（建议）**：**个股池一律剔除，指数成分记录保留**。

- 个股池（评分候选、K线/分红/财报抓取、前端个股列表、回测分组、持仓可选项）→ 全部排除；
- 指数成分记录（`红利指数与ETF成分股.md`、`components.json`、`_成分股汇总.json`）→ **保留以维持权重和完整**，但标注"无行情数据、不参与计算"；
- 若选择连成分记录一并剔除，代价是：中证红利价值权重和缺 1.39%、中证全指红利质量缺 0.04%，指数加权股息率与成分数将与官方样本文件不一致。**这是需要确认的取舍点**（详见附录 C.3）。

**落地方式**：在 `scripts/_common.py` 增加唯一判定 `is_bj(code)`（`startswith(("43","83","87","88","92"))`），并在**池构造点**统一调用：`_recommend_stocks.py`（候选池硬过滤，权威点）、`_fetch_stock_data.py:57-75`、`_fetch_pool_data.py:33-43`、`_gen_web_data.py:223/240`、`_gen_analysis.py:369`、`_update_summary.py`、`_fetch_watchlist.py`（当前无命中，加护栏）。清理清单见 **附录 C**。

**⚠️ 剔除不能掩盖的通用缺陷（保留 P0）**：本次事故的真正根因不是"北交所"，而是三个通用缺陷——它们对**任何**停牌/退市/改名/接口变更的标的同样成立：

1. **空返回被当成成功**：`_fetch_history.py:207-232` 收到 `[]` 仍写 `fetched_at=today`，于是"每天成功、新增 0 条"永远不进失败清单；
2. **`status` 每组只抽查 1 只**：`update.py:148-157` 的 `pick()` 只取每组第一个 `ready` 标的日期，单只滞后完全不可见；
3. **无 per-stock 新鲜度字段**：`manifest.json` 只有全局 `data_date`，`_gen_web_data.py:179` 用 `max(dates)` 掩盖单只滞后，前端无法标灰。

**方向**：① `update_incremental` 在"rows 为空且 `last_date` 落后今日 >3 交易日"时报错/入失败清单；② `status` 每组输出 min/中位/max + 滞后 >2 交易日的 code 清单；③ manifest 增加 `ind_last` 供前端标记陈旧。**这三条与是否保留北交所无关，建议无条件落地。**

### 1.2 回测执行日与文档口径差 1 天（研究有效性）

- `scripts/_backtest_analysis.py:63-64` 判定"t 日收盘确认信号"，`:73` 却用 `close[i]`（**信号确认日收盘**）作为买入价 → 隐含当日收盘成交。

- 项目自己的 `docs/改进方案-代码质量专项.md:209-212` 已记录并**决定暂缓**（决策点 1）。
- **方向**：这条直接决定"指数 12M 超额 +24%"这类核心结论是否被高估，建议从"暂缓"提升为"独立课题优先"：把 `+1` 改 `+2` 重跑 `update.py bt` + 组合回测，对比结论是否反转，再决定是否修正。

### 1.3 推荐 20 分组与名单的同步护栏

- 现状：`web/data/backtest.json` 的 `scope.groups` = 指数 11 / ETF 12 / 其他成份股 295 / **推荐20 19** / 自选股 48（合计 385）。缺的 1 只正是 920599（`_backtest_analysis.py:225` 用 `fsd.STOCKS` 含它，而 `_gen_analysis.py:369-377` 的 `enough_history` 要求 ≥60 日把它剔除）。
- 剔除北交所后该缺口自然消失，但**同类缺口无护栏**：`_test_analysis.py:298-336` 只校验"分组数之和 == 有效标的数"，该式恒成立。

### 1.4 因子覆盖率护栏（降级为 P1 潜在风险）

- 机制：`scripts/_recommend_stocks.py:225-241` 对缺失因子按剩余权重归一化 → 缺得越多、越容易被"提纯"成高分。

## 2. 最大杠杆：数据体积与传输

### 2.1 `analysis_dy.json` 30.7MB，前端实际只用 81KB（0.26%）

实测构成：

| 项                                 |            体积 |          占比 |
| :--------------------------------- | --------------: | ------------: |
| 全文件                             |         30.7 MB |          100% |
| `series` 字段合计                |         27.9 MB | **91%** |
| ├ 股票 series（1,379,825 点）     |         26.2 MB |           85% |
| ├ ETF series                      |          0.9 MB |            3% |
| └ 指数 series                     |          0.8 MB |            3% |
| **剥掉 series 后的全部标量** | **80 KB** |         0.26% |
| 仅保留近 5 年窗口（1250 点）       |         9.16 MB |           30% |

**关键点：股票的 series 前端从来没读过。**

- `web/js/views/compareView.js:270-274`：股票的 dy 序列来自 `indiUrl(code)`（指标文件），不是 analysis_dy；
- `:275-278`：只有指数/ETF 才读 `analysis_dy.series`；
- 其余用途（`scanView.js:32-35`、`reco.js:53-56`）只取 `series[series.length-1][0]` 拿一个 maxDate。

而 scan / recommend / holdings 三个视图**全量加载**它：`scanView.js:12,19`、`recommendView.js:13,20`、`holdingsView.js:14,24`。
前端实测代价：**JSON.parse 257–312 ms，堆内存 +232 MB**。

**优化方向**：Python 侧一次写出 `web/data/dy_meta.json`（去 series + 顶层 `max_date`，约 81KB），三视图改读它；指数/ETF 的 series 拆成按需文件供 compare 用。
**收益：三主视图省 30.6 MB 下载 + 约 300 ms 解析 + 约 230 MB 堆**，弱网/移动端从"不可用"变可用。

### 2.2 交付层零压缩 + `no-store`，每次刷新重下约 32MB

- `serve.py:52-56` 对所有响应加 `Cache-Control: no-store`；**没有任何 gzip/brotli**（curl 带 `Accept-Encoding: gzip` 实测仍返回原尺寸，无 `Content-Encoding`）。
- 冷启动进「智能推荐」≈ **32.3 MB 未压缩**；`web/js/theme.js:11-14` 的主题切换是 `location.reload()`，每次切换重走一遍。

实测压缩比（gzip -6）：

| 文件                            |      原始 |     gzip | 比例 |
| :------------------------------ | --------: | -------: | ---: |
| `cache/analysis_dy.json`      | 31,475 KB | 5,686 KB |  18% |
| `cache/股票_600036.json`      |    926 KB |   189 KB |  21% |
| `web/data/stocks/600036.json` |    588 KB |    67 KB |  11% |
| `web/data/backtest.json`      |    935 KB |   150 KB |  16% |

**优化方向**：① serve.py 对 `.json/.js/.css` 加 gzip（stdlib 约 15 行）；② `/cache`、`/web/data` 改 `Cache-Control: no-cache` + ETag（或按 `data_date` 版本化 URL），JS/CSS 保留 `no-store`。
**注意**：缓存策略写错会读到旧数据，务必保留 ETag 强校验或版本化。

### 2.3 字段级冗余（可再省一半）

`web/data/stocks/*.json` 共 1,457,403 行，字段字节占比：

| 字段                               |  占比 | 问题                                                                                                           |
| :--------------------------------- | ----: | :------------------------------------------------------------------------------------------------------------- |
| `d`（日期）                      | 26.3% | 与`cache/股票_*.json` 的 `date` 列**完全重复**（实测两文件日期集合一致，重复 13.9 MB）               |

编码方式对比（`cache/股票_600036.json`，5438 行）：

| 编码             |   体积 |          相对 |
| :--------------- | -----: | ------------: |

### 2.4 `cache/` 与 `web/data/` 双份存储

**方向**：合并为单一"发布产物"，或至少去掉重复日期列；同时保持"cache = 原始、web/data = 发布"的分层语义。

## 3. 仓库膨胀：.git 584MB，约 84MB/月

实测：**210 个 commit（2026-08-02 → 09-08，5 周）、pack 584.55 MiB、另有 22.56 MB 垃圾对象**；源码只有约 1 MB。按当前速率约 7 个月触及 GitHub 1 GB 软上限。

**根因（已用 git 证据锁定）**：`scripts/_fetch_history.py:198-232` 的 `update_incremental` **无条件** `save_cache`，且每次把 `fetched_at` 写成当天日期。于是：

| commit                          |    改动文件数 | 情形                                                 |
| :------------------------------ | ------------: | :--------------------------------------------------- |
| `a8d1bac6`（08-31）           | **777** | 新日历日 →`fetched_at` 让**每个**文件都变   |
| `666f6484`（08-31，同日重跑） |            34 | 同日`fetched_at` 相同 → 只有真变动的文件才有 diff |

这说明 `.github/workflows/daily-update.yml` 里那段"无数据变化 → 不提交"（`git diff --quiet`）在跨天运行时**永远不可能触发**：节假日/周末跑一次也会产生一个 770 文件的纯噪声 commit。

**优化方向**（尊重"缓存随 git 提交、误删可恢复"的既定约束）：

1. **只在数据真变化时写盘并更新 `fetched_at`** —— 改动最小、收益最直接：消掉全部噪声 commit；
2. 数据落盘体积压下来（第 2 节的列式 + gzip），每个 delta 同比缩小 5-8 倍；
3. 长期：把 `cache/` + `web/data/` 迁到**独立 orphan 分支 + 定期 squash**，主分支只留代码，同时保留"可恢复"能力。

### 4.2 前端直读 `cache/`，缺数据契约

`web/js/data.js:21-27` 的 `klineUrl` 直接拼 `/cache/${kind}_${code}.json` —— 前端依赖的是**内部抓取缓存**的目录布局，绕过了 `web/data/` 这个发布层。

- 后果：缓存格式一改前端静默坏掉；
- 所有产物**都没有 schema 版本字段**（`manifest` / `analysis` / `backtest` 均无 `version`）。

**方向**：K 线也走 `web/data/`（或显式声明 cache 为公开接口），并给每个产物加 `schema_version` + `data_date`。

### 4.3 静默失败缺少出口

- `scripts/_fetch_history.py:207-232`：fetcher 返回 `[]` 也照写 `fetched_at=today` → "成功"掩盖冻结（详见 §1.1）。

### 不建议做的

- **引入 bundler**：`web/js` 仅 5006 行 / 311 KB，相对 32 MB 数据包是噪声级；只建议给 `echarts.min.js` 加 `defer` + 首屏 `modulepreload`。
